# SYS-01 In-flight work 和长尾延迟是什么意思？

**标签**

`#SystemDesign` `#InFlightWork` `#TailLatency` `#并发控制` `#背压` `#性能指标`

## 问题

In-flight work 是什么意思？长尾延迟（Tail Latency）是什么意思？两者有什么关系？

## 面试回答

**In-flight work（在途工作）**通常指已经发出或开始处理、但尚未完成的请求、消息或任务。它可能正在计算，也可能在等待数据库、网络或下游服务，并不等于正在占用 CPU。

**长尾延迟**指大多数请求较快完成，但少量请求明显更慢，使延迟分布的右侧拖出较长的尾巴。通常使用 P95、P99、P99.9 等高分位数观察，而不能只看平均值。

两者会相互影响：请求变慢会让更多工作同时滞留；当资源接近饱和时，过多在途工作又可能增加排队和资源争用，进一步拉高延迟。因此需要结合并发限制、背压、超时和过载保护控制在途工作量。

## 详细解释

### 1. In-flight work 的统计边界

以一次 HTTP 请求为例：

```text
发出请求
   ↓
等待网络 / 下游服务 / 数据库
   ↓
执行与处理结果
   ↓
收到响应或操作结束
```

在所定义的开始和结束之间，该请求属于 in-flight。

不同系统的统计口径可能不同，面试时应先明确边界：

| 场景 | 常见的 in-flight 含义 |
| --- | --- |
| HTTP 客户端 | 已发出、尚未结束的请求 |
| 应用服务 | 已接收、尚未完成的请求，是否包含内部排队需看定义 |
| 消息消费者 | 已交付、尚未 ACK 的消息，具体看客户端和 Broker 的指标口径 |
| 任务执行器 | 已认领或已启动、尚未结束的任务 |

**仍在外部队列等待领取的任务，通常算 backlog，而不是 worker 的 in-flight work。**如果统计整个系统内尚未完成的工作，则可以将排队任务也包括在内，但必须说明口径。

例如，队列有 1,000 条待领取消息，worker 已领取 20 条且尚未完成：

```text
Backlog          = 1,000 条
Worker in-flight =    20 条
```

这 20 条中可能有 5 条正在计算，15 条等待 I/O；它们仍全部属于 in-flight。

客户端超时也不意味着服务端工作立即结束。取消操作需要传播到下游，并由下游支持和执行，否则服务端仍可能继续工作。

### 2. In-flight 数量与 QPS 的区别

- **QPS / 吞吐率**：单位时间内处理多少请求，单位为次/秒。
- **In-flight 数量**：某一时刻尚未完成的请求有多少，单位为个。
- **延迟**：一次请求从定义的开始到结束经历多久，单位为毫秒或秒。

在稳定系统中，按照一致的统计边界，Little’s Law 给出平均量关系：

```text
L = λ × W

L：边界内平均工作数量
λ：进入该边界的有效平均到达率（稳定时与完成率一致）
W：工作在该边界内的平均停留时间
```

例如，在途请求边界从发出到完成：

```text
1,000 次/秒 × 0.1 秒 = 平均约 100 个在途请求
1,000 次/秒 × 1   秒 = 平均约 1,000 个在途请求
```

第二个例子假设系统仍能稳定承受该流量。若到达率长期超过处理能力、队列持续增长，就不能用一个稳定平均值推断系统状态。

如果 L 包含排队任务，W 也必须包含排队时间。该公式使用平均值，不能直接将 P99 代入计算平均在途数量。

### 3. 什么是长尾延迟

以下是一组假设的监控结果：

| 指标 | 延迟 | 含义 |
| --- | --- | --- |
| P50 | 50 ms | 约 50% 的请求在此时间内完成 |
| P95 | 200 ms | 约 95% 的请求在此时间内完成 |
| P99 | 2,000 ms | 约 99% 的请求在此时间内完成 |

在同一个统计窗口内，P99 = 2 秒意味着约 1% 的请求比 2 秒更慢；它不是“99% 的请求都耗时 2 秒”。

P99 也不是最大延迟。高分位数用于观察尾部，但长尾没有固定的秒数门槛，应结合延迟分布和业务目标判断。

常见原因包括：

- 数据库慢查询、锁等待或热点争用；
- GC 暂停、CPU 调度或线程池不足；
- 连接池耗尽、内部排队；
- 缓存未命中导致走较慢路径；
- 网络波动、下游变慢或重试。

### 4. 为什么平均延迟不够

假设 1,000 个请求中：

```text
990 个请求耗时 50 ms
 10 个请求耗时 5,000 ms

平均延迟 = (990 × 50 + 10 × 5,000) / 1,000
         = 99.5 ms
```

平均值不到 100 ms，但其中 10 个请求等待了 5 秒。应同时观察高分位数、延迟直方图、超时率和错误率。

分位数有多种计算方法，恰好位于百分位边界的样本可能得到不同结果，因此不能仅凭这个示例断言某个工具计算出的 P99 一定为 5 秒。

### 5. Fan-out 为什么会放大慢请求的影响

假设一个页面并行调用 100 个下游，且必须等待全部结果。若每个下游独立地有 1% 的概率超过某个延迟阈值，那么至少一个下游超过该阈值的概率为：

```text
1 - (1 - 0.01)^100 ≈ 63.4%
```

这是独立性假设下的示例；实际下游可能存在相关性。它说明：单个下游少量的慢请求，可能显著影响聚合请求。端到端延迟通常还包含网关、网络和聚合处理开销。

## 故障场景

### 场景 1：下游变慢导致在途请求堆积

```text
数据库变慢
   ↓
请求等待更久
   ↓
在途请求数量增加
   ↓
连接、内存等资源压力增加
   ↓
排队和争用加剧
   ↓
更多请求变慢或超时
```

处理思路：

- 限制并发和队列长度，容量不足时背压或拒绝新工作；
- 设置合理的端到端 deadline，并向下游传播超时与取消；
- 对可重试操作采用有限次数、退避与抖动，避免重试放大负载；
- 优化慢查询与热点，必要时降级或扩容。

提高并发上限不一定提高吞吐量；资源饱和后可能只会增加延迟。

### 场景 2：客户端超时后立即重试

旧请求可能仍在服务端执行，新请求又进入系统，导致在途工作增加。涉及写操作时还可能重复产生副作用，因此应结合取消传播、重试预算和业务幂等处理。

### 场景 3：服务停机时还有工作未完成

优雅停机通常先停止接收新工作，再给已有 in-flight work 一段有限时间完成。超过期限后，需要根据任务语义处理取消、持久化恢复或消息重新投递，避免仅凭“进程退出”认定业务完成。

## 关键结论

- In-flight work 是已经进入指定处理阶段、尚未完成的工作；必须明确统计边界。
- 等待 I/O 的工作也属于 in-flight，不要求持续占用 CPU。
- 长尾延迟关注少量显著较慢的请求，常用高分位数观察。
- QPS、在途数量和延迟是不同维度；稳定条件下可用 Little’s Law 联系平均量。
- 下游变慢与过多在途工作可能形成过载反馈循环。
- 控制并发和排队、合理设置超时与重试，有助于保护系统。
