# REDIS-01 Redis 如何实现 Rate Limit（限流）？

**标签**

`#Redis` `#RateLimit` `#分布式限流` `#Lua` `#原子性` `#固定窗口` `#滑动窗口` `#令牌桶`

## 问题

Redis 如何实现 Rate Limit？例如“同一个用户，每个 60 秒窗口最多请求某个 API 100 次”，多个应用实例如何共享额度？为什么需要 Lua？固定窗口、滑动窗口和令牌桶有什么区别？

## 面试回答

Redis 保存多个应用实例共享的限流状态，应用或网关在处理请求前，执行一次原子的检查与更新，根据结果放行或拒绝。

最简单的方案是 **计数器 + 过期时间**：按用户、API 等维度构造 Key，用 INCR 计数，首次创建计数器时设置 60 秒过期。计数不超过 100 则放行，超过则由应用返回 HTTP 429。

虽然 INCR 本身是原子的，但 INCR、首次设置过期和额度判断的组合需要统一处理。可以使用 Lua 在 Redis 中完成，避免应用并发检查以及两次命令之间中断带来的问题。

固定窗口简单，但边界附近可能出现突发。需要精确限制最近 60 秒内的请求数时，可使用 Sorted Set 实现滑动窗口日志；需要控制平均速率并允许一定突发时，可使用令牌桶。

## 详细解释

### 1. Redis 和应用各自负责什么？

```text
请求到达应用 / API 网关
            ↓
确定用户、API 和限流规则
            ↓
向 Redis 执行原子限流操作
            ↓
      是否还有额度？
       ├─ Yes → 执行业务
       └─ No  → 返回 429 Too Many Requests
```

Redis 提供共享状态与原子操作，通常不是由 Redis 直接拦截 HTTP 请求。真正执行放行、返回状态码或其他策略的是应用或网关。

限流维度可以是用户、租户、IP、API Key 或接口。例如：

```text
ratelimit:orders:user:123
```

表示用户 123 对订单接口这一规则的状态。所有需要共享额度的实例必须使用一致的 Key 构造方式、规则和权威写入路径。

### 2. 固定窗口计数器如何工作？

假设使用一个固定 Key，从首次请求开始一个 60 秒窗口：

```text
Key   = ratelimit:orders:user:123
Value = 当前窗口的请求计数
TTL   = 窗口剩余时间
Limit = 100
```

处理过程：

1. 请求到达，执行 INCR，Key 不存在时从 1 开始。
2. 如果是窗口中的第一次请求，设置 60 秒过期。
3. 计数小于或等于 100，则放行。
4. 计数大于 100，则拒绝。
5. Key 过期后，下一个请求创建新的窗口。

这里只在首次创建窗口时设置过期，后续请求不会延长窗口。

这个示例的窗口从首次请求开始，不是自然分钟的 12:00:00～12:00:59。若需要按自然分钟对齐，可以采用包含时间桶的 Key，但必须另外处理各实例的时钟和边界口径。

### 3. 为什么单个 INCR 原子还不够？

一种不完整的实现是分别发送：

```text
INCR key
    ↓
如果结果为 1，则发送 EXPIRE key 60
```

如果应用在 INCR 成功后、EXPIRE 发出前断开，计数器可能没有过期时间，之后也不能正常开始新窗口。

另一个常见错误是先读取计数再在应用中写回：

```text
实例 A 读取 count = 99
实例 B 读取 count = 99
实例 A 判断可放行，写回 100
实例 B 判断可放行，写回 100
```

这会导致并发判断超额及计数丢失。应把需要共同生效的检查与更新放在 Redis 中执行，而不是依赖多个应用实例之间的本地判断。

### 4. 固定窗口 Lua 示例

下面使用常见的 INCR、PEXPIRE 和 PTTL 命令。示例约定此 Key 专用于整数计数，且由该限流逻辑维护。

```lua
-- KEYS[1]: 限流 Key
-- ARGV[1]: 请求上限，例如 100
-- ARGV[2]: 窗口毫秒数，例如 60000

local limit = tonumber(ARGV[1])
local windowMs = tonumber(ARGV[2])

-- 在修改状态前检查参数
if not limit or limit < 1 or limit ~= math.floor(limit)
   or not windowMs or windowMs < 1
   or windowMs ~= math.floor(windowMs) then
    return redis.error_reply("limit and windowMs must be positive integers")
end

local count = redis.call("INCR", KEYS[1])

if count == 1 then
    redis.call("PEXPIRE", KEYS[1], windowMs)
end

local allowed = 0
if count <= limit then
    allowed = 1
end

return {allowed, redis.call("PTTL", KEYS[1])}
```

参数示例：

| 参数 | 值 |
| --- | --- |
| KEYS[1] | ratelimit:orders:user:123 |
| ARGV[1] | 100 |
| ARGV[2] | 60000 |

返回值：

| 位置 | 含义 |
| --- | --- |
| 第一个值 | 1 表示允许；0 表示限流 |
| 第二个值 | 窗口剩余毫秒数 |

应用收到 0 时返回 429，并可把非负的剩余毫秒数向上换算为秒，设置 Retry-After。PTTL 返回 -1 表示 Key 没有过期时间，-2 表示 Key 不存在；这些值应按异常状态处理，不能当作正常等待秒数。

这个实现会将被拒绝的请求也计入计数，但只在首次创建窗口时设置 TTL，所以持续发送被拒绝的请求不会一直延长窗口。计数表示进入该限流检查的请求尝试次数，不代表业务成功次数。

Lua 的原子执行意味着同一节点上，其他请求不能穿插修改脚本正在处理的状态。脚本应保持简短，避免长时间占用 Redis 的执行路径。命令错误、超时和故障切换仍需独立处理。

### 5. 多个应用实例如何共享额度？

```text
应用实例 A ─┐
应用实例 B ─┼→ 同一权威 Redis 节点上的同一用户 Key
应用实例 C ─┘                 ↓
                    共同使用一个窗口的 100 次额度
```

假设有 20 个实例，每个都在本地独立允许 100 次，则全部实例合计可能允许 2,000 次。使用共享 Redis 状态后，正常运行下，各实例对同一 Key 的请求共同计数。

关键不是“使用了 Redis”这一点本身，而是所有实例是否实际检查同一个额度。不同 Key、绕过检查的请求，或各自独立的数据副本，都不能自动组成严格统一的限流器。

Redis Cluster 下，一个 Key 会路由到对应分片；若脚本需要操作多个 Key，还需满足同槽等约束，不能假设跨分片的任意多 Key 操作天然原子。

多 Key 的执行边界、hash tag 与错误不自动回滚的说明，参见 [REDIS-02 Redis Lua 可以跨多个 Key 实现原子操作吗？](REDIS-02-lua-multi-key-atomicity-and-cluster-slots.md)。

### 6. 固定窗口为什么有边界突发？

假设旧窗口结束前，用户集中用完剩余额度；新窗口开始后，又立即用完新的额度：

```text
旧窗口结束前：集中消耗旧额度
              │ 窗口边界
新窗口开始后：立即消耗新额度
```

每个独立窗口都未超过 100 次，但跨边界的一小段时间可能放行超过 100 次。

因此：

```text
每个固定窗口最多 100 次
```

不等于：

```text
任意连续 60 秒最多 100 次
```

也不能通过“每次请求都重新设置 60 秒 TTL”把计数器变成精确滑动窗口；那样会改变窗口语义，并可能导致持续请求时窗口迟迟不结束。

### 7. 常见算法的区别

| 算法 | Redis 状态 | 规则与取舍 |
| --- | --- | --- |
| 固定窗口 | 整数计数器 + TTL | 简单、状态少；窗口边界可能突发 |
| 滑动窗口日志 | Sorted Set 保存请求时间戳 | 可精确统计最近一段时间；内存随保留的请求数增长 |
| 滑动窗口计数器 | 相邻时间桶计数及权重 | 用较少状态近似滑动窗口，存在估算误差 |
| 令牌桶 | 剩余令牌数、上次补充时间 | 控制平均速率，同时允许桶容量范围内的突发 |

滑动窗口日志的核心步骤是：

```text
移除窗口外记录
      ↓
统计窗口内记录
      ↓
未达到上限时，加入本次请求记录并放行
```

这些步骤应原子完成。Sorted Set 的 score 可用时间戳，member 应有唯一标识，避免同一毫秒的不同请求被覆盖。时间口径和窗口左右边界也需要统一。

令牌桶的核心计算是：

```text
补充后令牌 = min(桶容量, 原令牌 + 补充速率 × 已经过的时间)

令牌足够 → 扣减本次消耗并放行
令牌不足 → 拒绝
```

通常可以在请求到达时按时间差计算补充量，不必真的每秒运行任务逐个增加令牌。令牌桶也不等于任意连续窗口的精确请求次数上限。

### 8. 限流不等于并发限制

“60 秒内允许 100 次”限制的是请求速率，不能直接保证“最多只有 100 个请求正在执行”。

请求如果很慢，不同时间到达的工作仍可能积累。保护下游数据库时，可能需要同时采用速率限制、请求并发上限、超时和背压。

相关概念参见 [SYS-01 In-flight work 和长尾延迟](../system-design/SYS-01-in-flight-work-and-tail-latency.md)。

## 故障场景

### 场景 1：INCR 成功，设置过期前应用断开

分开发送命令可能留下没有 TTL 的计数器。使用原子 Lua 组合正常路径，避免客户端在两次调用之间中断造成的这个窗口；同时检查已有 Key 的状态和命令错误。

### 场景 2：多个实例各用不同 Key

例如 Key 中额外包含应用实例编号，则每个实例获得独立额度，无法实现原本期望的用户全局额度。需要明确限流维度并统一命名。

### 场景 3：Redis 超时或不可用

必须预先定义降级策略：

| 策略 | 行为 | 代价 |
| --- | --- | --- |
| Fail-open | Redis 异常时允许请求，或退化为本地保护 | 可能超过分布式额度 |
| Fail-closed | Redis 异常时拒绝请求 | 依赖故障会影响正常用户 |
| 本地限流降级 | 临时按各实例本地额度保护 | 不再具有同一份全局计数 |

“无法查询限流状态”与“确定额度耗尽”不同，不应把 Redis 故障一概伪装成 429。还应限制等待 Redis 的时间，避免限流检查本身拖慢整个请求链路。

### 场景 4：故障切换或数据淘汰导致计数状态丢失

Redis 主从复制通常是异步的，故障切换可能丢失部分已确认的计数更新。Key 提前被淘汰或删除也可能让窗口重新开始，从而额外放行请求。

Lua 的并发原子性不等于故障期间的全局精确额度保证。对额度严格程度有要求时，需要结合部署、复制、持久化与故障策略评估。

### 场景 5：客户端没收到 Redis 的执行结果就重试

原子脚本可能已经成功更新计数，但应用只看到超时。再次执行可能再次计数，因此该简单示例不保证每个业务请求只消耗一次额度。是否需要按请求标识去重，应由限流规则决定。

## 关键结论

- Redis 通过共享状态和原子操作支持分布式限流，应用或网关负责实际放行与拒绝。
- 常见固定窗口实现使用 INCR、过期时间与 Lua。
- 本文示例从首次请求启动窗口，统计请求尝试次数，后续请求不会延长窗口。
- 固定窗口边界可能突发；滑动窗口日志与令牌桶解决的是不同的速率约束需求。
- 所有实例必须针对同一限流维度检查同一份额度。
- 速率限制不能替代请求并发控制。
- 超时、重试、故障切换及状态丢失都可能影响计数语义，需明确策略。
