# DB-06 主主复制何时发生脑裂？节点数量与网络分区如何影响仲裁？

**标签**

`#Database` `#Replication` `#MultiPrimary` `#SplitBrain` `#Quorum` `#NetworkPartition` `#Fencing` `#HighAvailability`

## 问题

主主复制架构在什么情况下会发生脑裂？至少需要几个可写主库，为什么又常说需要三个节点？如果两个主库都无法联系第三个投票节点，是否必须停止写入？如果三个节点彼此隔离，又会怎样？

## 面试回答

主主架构中，多个节点同时接收写入是正常能力。脑裂关注的是：本应遵守同一套仲裁或提交规则的集群分裂为互不协调的部分，而多个部分仍独立认为自己拥有有效写入资格，形成相互冲突的权威状态。

主主从定义上至少有两个可写主节点。但可写主节点数与投票节点数是不同概念。在固定成员、每节点一票的多数派模型中，要容忍一个投票节点突发失联并继续取得多数派，至少需要三个投票节点。

假设 A、B、C 是同一仲裁组中的三票：

- A、B 仍可互通，只与 C 失联：A、B 有 2/3 票，可以在满足其他提交条件后继续；C 侧没有多数派。
- 三者彼此隔离：各自只有 1/3 票，没有任何一侧能完成需要多数派确认的写入。

C 只是三票之一，不是每笔写入都必须单独批准的中央裁判。若 C 是另一套外部仲裁服务，则要按其自身的租约、成员和故障恢复机制分析，不能直接套用上述票数。

## 详细解释

### 1. 正常多主与脑裂有什么区别？

正常多主允许多个写入入口。写入仍需要遵守系统设计的复制、冲突检测或提交协调规则。

例如，MySQL Group Replication 的多主模式中，正常且兼容的组成员可以并发接收写事务，但仍属于同一复制组。多个入口可写不意味着它们可以脱离组协议，独立确认需要共同协调的事务。

本笔记讨论的故障意义上的脑裂，强调集群应维持的写入资格或提交规则被破坏。即使暂时没有两边修改同一条记录，两个不兼容的权威组同时提供服务也可能已经构成脑裂；同一数据的冲突会进一步暴露其后果。

| 情况 | 如何理解 |
| --- | --- |
| 正常多主并发写入，遵守既定协调规则 | 正常架构能力 |
| 网络分区后，少数派无法完成需要仲裁的提交 | 防止脑裂的保护行为 |
| 原多数派仍运行，少数派又被强制建立成独立可写组 | 可能人为制造脑裂 |
| 异步多主按设计允许分区写入并保留冲突版本 | 需要按其一致性模型判断，不能仅因多处可写就认定故障脑裂 |

### 2. 哪些情况容易造成脑裂？

最典型的诱因是网络分区：数据库节点无法互通，但不同客户端仍然能够访问各侧。

```text
客户端 1 → 主库 A   ×   主库 B ← 客户端 2
                    节点间失联
```

如果这些写入本应共同协调，却在失去有效协调后仍被各侧独立确认，就可能形成不兼容的历史。

例如，业务要求最后一件商品只能卖出一次：

```text
分区前：
    A、B 都知道库存为 1

分区后，假设错误地允许两侧独立提交：
    A 接受订单 X，扣减成功
    B 接受订单 Y，扣减成功

结果：
    两个客户都被告知购买成功
```

网络分区本身不必然造成脑裂，还需要观察系统是否继续允许不兼容的提交或写入权威。

其他常见原因包括：

- **强制恢复不当**：未确认另一侧已经停止，就在本侧强制重建成员或覆盖仲裁状态。
- **旧节点隔离失效**：已失去写入资格的节点仍能确认有效业务写入。
- **成员配置不一致**：不同部分按不兼容的成员配置运行，各自认为具备合法仲裁资格。

只根据“联系不上”不能确定对端已经宕机。对端可能仍在另一个网络分区服务客户端。

### 3. 至少需要几个主库或投票节点？

先区分角色：

| 角色 | 职责 |
| --- | --- |
| 可写主节点 | 接收业务写入请求 |
| 数据副本节点 | 保存数据并参与复制；是否可写取决于产品和模式 |
| 投票节点 | 按协议参与仲裁；可能同时承担数据副本角色 |
| 见证节点 | 在支持它的产品中提供仲裁信息或投票，通常不保存完整业务数据 |

主主至少需要两个可写主节点。容错数量则取决于实际仲裁组及提交协议，不能仅计算主库个数。

以下假设固定成员、每节点一票，且成员按同一有效配置运行：

```text
多数派票数 Q = floor(N / 2) + 1

要在任意 f 个投票节点突发失联后仍保有多数派：
    至少需要 N = 2f + 1 个投票节点
```

| 投票节点数 N | 多数派 Q | 最多可突发失联多少个节点后仍有多数派 |
| --- | --- | --- |
| 2 | 2 | 0 |
| 3 | 2 | 1 |
| 4 | 3 | 1 |
| 5 | 3 | 2 |

这说明在此模型中，两个节点彼此断连后，各自的一票都不足以形成多数派。三个节点则可以在分成 2 + 1 时保留一个多数派。

奇数不是自动防脑裂的机制。表格只描述仲裁数量，实际提交还要求相应的数据状态、协议执行和恢复条件成立。

### 4. 两个主库都与第三个投票节点分区，会怎样？

关键是 A、B 之间是否仍能协调。

**情况一：A、B 互通，C 被隔离。**

```text
[A ↔ B]     ×     [C]
  2/3             1/3
有多数派        没有多数派
```

A、B 合计取得两票，已经超过三票的一半。它们可以在完成必要的故障检测、成员处理或选举，并满足其他提交条件后继续推进。

C 不必每次都单独批准写入。C 的失联也不意味着 A、B 失去彼此的票。

如果 C 本身是可写数据节点，它不能脱离有效多数派独立确认需要仲裁的写入；如果它只是见证，它本来就不承担业务写入。

**情况二：A、B 之间也不通，三者彼此隔离。**

```text
[A]     ×     [B]     ×     [C]
1/3           1/3           1/3

三者之间均无有效通信
```

没有任何一侧达到两票，都无法完成需要多数派确认的写入，可能表现为阻塞、超时或报错。它们不能仅因自己仍在线，就把自己的票当成多数派。

这时停止相关提交是在避免互不兼容的提交历史。是否仍能提供部分读取，以及读取具有什么一致性保证，需要按具体产品分析。

### 5. 三节点分区结果汇总

下表仍采用同一个三票仲裁组、每节点一票的简化模型：

| 可协调的分组 | 各组票数 | 仲裁结果 |
| --- | --- | --- |
| A、B、C 相互可协调 | 3 | 集群可以按协议推进 |
| A、B 一组；C 单独 | 2 + 1 | A、B 一侧有多数派 |
| A、C 一组；B 单独 | 2 + 1 | A、C 一侧有多数派 |
| B、C 一组；A 单独 | 2 + 1 | B、C 一侧有多数派 |
| A、B、C 各自隔离 | 1 + 1 + 1 | 所有侧都没有多数派 |

“有多数派”表示具备继续协调的必要条件，不表示表中每个节点都可写，也不单独保证任意数据复制要求都已满足。

特别是 C 仅为见证时，A、C 有仲裁资格，不代表业务数据一定已经安全复制到两份。是否允许只剩一个数据节点时提交，仍取决于实际产品与数据确认策略。

多数派也不是简单数能 ping 通几个地址。投票必须遵守具体协议对提案、任期或日志状态等的约束，共同节点不能批准互不兼容的决定。应用不能自行把两组“我加一个可达节点”都认定为有效多数派。

### 6. 第三个投票节点是否必须是第三个主库？

不一定，但必须由产品支持相应的角色设计。

- 如果采用完整数据成员参与共识，第三个节点需要保存数据，并按该产品规则参与协议。
- 如果产品支持见证节点，它可以提供仲裁能力，但不等于额外的数据副本。
- 如果使用独立的外部仲裁服务，应计算该服务自己的成员和多数派，不能把两个数据库进程直接视为它的两票。

以 MySQL Group Replication 为例，为容忍一个成员突发故障，复制组需要三个成员。多主模式下，正常且兼容的成员可以作为写入入口；这不是任意两个数据库加一台普通见证机器就能直接替代的配置。

写入资格的仲裁、业务数据的复制确认以及客户端成功响应的条件，是相关但不同的机制。

### 7. 如何防止和恢复脑裂？

在要求统一提交规则的系统中，应由数据库协议或高可用控制机制确保失去资格的一侧不能继续确认有效写入。

可采用的机制取决于产品，例如：

- 多数派共识或有效租约，约束哪些成员可以继续服务。
- 数据库自身阻止无资格节点提交。
- 必要的 Fencing，将旧节点置于不能有效写入的状态，例如停止服务或隔离节点。
- 恢复时检查成员身份与数据状态，重新同步后再加入有效组。

只把节点从负载均衡器移除，并不能替代提交资格检查：直接连接、旧连接或其他客户端仍可能到达它。

MySQL 官方文档指出，原来的多数派可能仍在运行；此时在少数派强制覆盖成员配置，会人为建立第二个可运行的组。不能仅因为本侧失去仲裁，就认为强制恢复一定安全。

实际恢复需要先确认有效成员、隔离状态和数据历史。

### 8. 所有主主架构都必须采用三节点多数派吗？

不是。主主描述多个写入入口，不能单独决定复制协议和一致性模型。

某些异步多主系统明确允许网络分区期间独立写入，再保存冲突版本或进行合并。CouchDB 的复制冲突模型就是保留并传播并发版本，再由相应机制处理。

这类预期的分歧与破坏仲裁规则的故障脑裂，应分别讨论。允许事后合并，也不代表能自动维持“最后一件库存只能卖出一次”等全局业务约束。

因此，“主主至少两个可写主节点”与“多数派模型容忍一个投票节点失联至少需要三票”是不同结论。具体部署数量要结合数据库协议和业务保证判断。

## 故障场景

### 场景 1：第三节点失联，被误认为整个集群必须停写

A、B 仍能互相通信，且本来就是同一三票组的两个有效成员。

它们仍拥有 2/3 票。需要检查其他协议与数据条件，不能仅根据 C 不可达就认定失去多数派。

### 场景 2：三个节点都在线，但三者互相隔离

每个节点都能响应本地客户端，却只能取得自己的一票。

在线不等于具备仲裁资格。此时各侧停止完成需要多数派的写入，是正确保护行为。

### 场景 3：强制恢复少数派时，原多数派仍在服务

原三节点组分成 A、B 与 C。A、B 仍有多数派，却有人将 C 强制重建成独立可写组。

这可能形成两个互不兼容的权威组。恢复前需要明确另一组状态并完成必要隔离，不能只依赖本侧探测结果。

### 场景 4：把见证票当成数据副本

一个数据节点与见证仍可形成产品要求的仲裁，但另一个数据节点不可达。

即使产品允许继续写入，也不能由仲裁票数推导出新增数据已有多份持久副本。应分别检查复制确认和故障切换的数据保护保证。

## 关键结论

- 主主允许多个写入入口；脑裂强调出现违反既定统一规则的不兼容权威状态。
- 网络分区是常见诱因，是否发生脑裂还取决于仲裁与提交资格是否被正确执行。
- 主主至少需要两个可写主节点，但主库数量不等于投票节点数量。
- 固定成员、每节点一票的多数派模型中，容忍 f 个投票节点突发失联至少需要 2f + 1 票。
- 三票组中 A、B 互通而 C 隔离时，A、B 有 2/3 票；三者各自隔离时，任何一侧都没有多数派。
- 第三票不必每次单独批准写入；但独立外部仲裁服务不能直接当作同一组中的第三票。
- 见证可以帮助仲裁，不能替代业务数据复制确认。
- 有多数派不等于所有数据库条件都已满足，也不自动保证零数据丢失。
- 强制改写成员配置前必须确认其他组状态与隔离条件。
- 异步多主是否允许分区写入，要结合它承诺的一致性模型与冲突处理机制判断。
