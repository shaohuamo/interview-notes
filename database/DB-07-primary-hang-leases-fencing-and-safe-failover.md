# DB-07 主从复制中主库假死，如何避免脑裂？

**标签**

`#Database` `#Replication` `#Failover` `#SplitBrain` `#Lease` `#Quorum` `#Fencing` `#SQLServer` `#HighAvailability`

## 问题

主从复制中，主库进程假死、心跳超时或与集群失联时，如何避免从库提升后出现两个可写主库？让旧主拒绝写入是否足够？租约、仲裁和 Fencing 各自承担什么职责？SQL Server Always On 如何处理这种风险？

## 面试回答

旧主失去写入资格后，必须停止确认有效写入。但不能仅依赖向假死主库发送一条只读或停止命令，因为它可能收不到命令，或者暂时无法执行管理逻辑。

心跳超时只是故障怀疑。高可用机制需要按仲裁规则确定有效的主角色，并在新主开放写入前，确认或通过协议保证旧主已经失去写入能力。常见机制包括租约到期后停止提交，以及在无法可靠自行停止时使用 Fencing 隔离旧主。

旧主恢复执行后也不能继续使用旧的写入资格；应按产品要求核对角色和数据状态，重新同步后作为从库加入。客户端通过 Listener、VIP 或代理连接新主，但路由切换本身不能取代旧主隔离。

SQL Server Always On AG 在 Windows 下通过 WSFC 与 SQL Server 之间的租约机制协调角色。租约无法续期时，对应 AG 可进入 resolving 状态并停止作为主副本服务，避免旧主与新主同时有效写入。

## 详细解释

### 1. “主库假死”为什么危险？

假死可能表现为：

- 高负载或资源等待导致心跳、健康检查迟迟没有响应。
- 管理进程无法运行，但数据库仍可能服务部分已有连接。
- 虚拟机或进程暂时暂停，稍后恢复执行。
- 主库与集群控制通道失联，但部分客户端仍可访问主库。

故障检测端不能只凭超时区分“已经停止”“暂时很慢”和“网络分区”。

危险的切换过程是：

```text
主库 A 暂时失去响应
        ↓
从库 B 被提升为主库并接收写入
        ↓
A 恢复，仍认为自己是主库
        ↓
旧连接或其他客户端继续向 A 写入
        ↓
A、B 形成不兼容的写入历史
```

防护目标是避免两个不兼容的主角色同时确认有效写入。脑裂与仲裁的基础概念参见 [DB-06 主主复制、脑裂与多数派仲裁](DB-06-multi-primary-split-brain-quorum-and-network-partitions.md)。

### 2. 为什么“通知旧主拒绝写入”不够？

发送管理命令依赖旧主能够收到并及时执行请求。假死、网络异常或控制进程故障，恰好可能使这一前提不成立。

即使应用已经连接新主，也可能还有旧连接、直连客户端或其他入口指向旧主。因此，不能把“已更新路由”当成旧主停止提交的证明。

如果旧主能够正常响应，可以按产品机制执行降级或停止服务。若无法可靠执行，应由租约或外部隔离措施确保其写入资格失效，而不是只发送命令后直接假定成功。

### 3. 仲裁、租约与 Fencing 的分工

| 机制 | 主要职责 |
| --- | --- |
| 仲裁 / Quorum | 按集群规则决定哪些成员有资格推进主角色变更 |
| 租约 / Lease | 使主角色的有效性具有受协议约束的期限，协调失去资格后的停止行为 |
| Fencing / 隔离 | 使旧节点无法继续有效写入，必要时不依赖其业务进程配合 |
| 路由入口 | 将新的客户端连接引导至有效主库 |

这些机制可以由数据库、集群管理器及独立设备共同实现，不要求每个机制都是一台独立服务器。

Fencing 的方式取决于产品和基础设施。例如通过受管理的电源或虚拟机控制重置节点，或在支持的存储体系中撤销旧节点的写入能力。

数据库自己按协议停止提交也是重要防线。并不是任何故障都必须断电；关键是能否可靠保证旧写入资格不再生效。

### 4. 租约如何处理暂停后恢复的旧主？

抽象地说，主角色的资格需要持续维持有效性：

```text
主角色资格仍有效
        ↓
按协议维护或续期
        ↓
无法维持有效资格
        ↓
在资格失效后停止提交
        ↓
恢复执行时不能沿用过期资格
```

具体产品的租约对象和续期路径并不相同，不能假设所有数据库都向同一台外部服务器续约。

租约还依赖产品规定的计时、故障检测与切换时序。应用里随意设置一个定时器，不能替代已验证的数据库或集群租约机制。

如果整个进程或虚拟机被暂停，普通进程内的检查也可能无法及时运行，需要结合产品支持的隔离保护。保护是否覆盖某种暂停或基础设施故障，要按部署机制判断。

### 5. 安全切换的过程

```text
检测到主库 A 超时或异常
        ↓
按仲裁和故障策略决定是否切换
        ↓
确认或由协议保证 A 已失去有效写入资格
        ↓
合格从库 B 完成必要恢复并成为新主
        ↓
客户端重新连接有效入口
        ↓
A 恢复后核对数据状态，重新同步并作为从库加入
```

这里的“保证旧主失去资格”不一定要求收到旧主返回的确认响应。符合要求的租约失效或外部 Fencing，可以在无法直接与旧主通信时提供保护。

如果无法确认或由协议保证旧主已经失去写能力，不能仅因希望尽快恢复服务，就随意开放另一个可写主库。

防止脑裂和避免数据丢失也需要分别判断。异步复制中，安全隔离旧主后提升落后的从库，仍可能丢失尚未复制的已提交修改。

### 6. SQL Server Always On AG 的例子

Windows 上的 AG 租约用于同步 SQL Server 与 WSFC 资源宿主对角色的认识。它不是“所有 SQL Server 都向一台见证数据库申请每笔事务的许可”。

SQL Server 的租约线程与资源宿主相互维护状态。租约到期或停止时，副本会针对该 AG 转入 resolving 角色。

故障切换中，资源管理器可以尝试让旧 AG 下线。如果管理调用失败或超时，租约失效路径用于保证旧主退出有效主角色，再使新主上线。

这里针对的是相应 AG 的角色与数据库可用状态，不应理解为 SQL Server 实例内所有无关数据库都会被统一设成只读。

自动切换还需要满足产品规定的目标副本同步状态、仲裁、故障策略等条件。租约只解决其中一部分角色协调问题。

### 7. Patroni Watchdog 的例子

Patroni 为 PostgreSQL 提供高可用控制。在正常情况下，无法维持 DCS 中的领导资格时，会尝试停止 PostgreSQL。

如果 Patroni 本身崩溃、停止数据库太慢或无法获得运行机会，正常停止路径可能失效。其 Watchdog 支持通过软件或硬件看门狗，在无法按要求获得心跳时重置节点，增加一层保护。

具体保护范围和时序要按 Watchdog、操作系统及虚拟化环境的要求配置；不能把同一故障域内任意软件定时器都视为可靠的独立保护。

这说明旧主自行停止与外部保护可以配合使用。不同产品的实现路径不同，不应把 Patroni 的 DCS 机制直接等同于 SQL Server AG 的本地租约机制。

### 8. 客户端入口与旧主恢复

客户端应通过稳定入口连接有效主库，但已有连接通常仍需要断开、重建。入口变化不会把旧数据库上的进行中事务无缝搬到新主。

写入可能已经提交，只是成功响应丢失。重试时要通过业务幂等键或执行结果查询避免重复副作用。

旧主恢复后，应按产品要求校验成员角色和数据历史。若已发生分叉，可能需要回退到共同历史或重新初始化，不能直接恢复可写角色。

节点和组件职责参见 [DB-08 主从 Failover 的节点与组件](DB-08-primary-replica-failover-node-roles-and-topologies.md)。

## 故障场景

### 场景 1：旧主收不到降级命令

控制通道失联，但旧主仍可服务部分客户端。仅发送只读命令后就提升新主，不能证明旧主已停止。

需要由产品的租约或隔离机制提供旧主失去有效写入能力的保证。

### 场景 2：虚拟机暂停后恢复

旧主暂停期间，从库已经成为新主；旧主恢复后继续执行旧路径。

有效的角色与租约检查、以及适用的 Fencing，必须防止它沿用旧资格确认写入。

### 场景 3：只修改负载均衡器

新请求被转发至新主，但旧连接或其他客户端继续访问旧主。

路由不是数据层的写权限裁定，应同时确保旧主不能继续有效提交。

### 场景 4：避免双主后仍丢失数据

旧主已隔离，但目标从库缺少部分已提交日志。

这属于复制持久性与恢复点问题。防脑裂不等于异步复制的零数据丢失。

## 关键结论

- 旧主失去有效写入资格后，必须停止确认有效提交。
- 超时不能证明对端已停止，也不能单独授权从库自行提升。
- 安全切换依赖仲裁，以及旧主租约失效或可靠隔离。
- 旧主可能无法执行管理命令，需要有不完全依赖其业务进程配合的保护。
- 新主开放写入前，旧主写入资格必须已经由机制保证失效。
- SQL Server AG 的租约与具体 AG 角色相关，不是为每笔事务向见证节点申请许可。
- 客户端路由、连接重建和请求幂等，是故障切换后的另一部分工作。
- 旧主重新加入需要校验和同步；防脑裂不能单独保证异步复制不丢数据。
